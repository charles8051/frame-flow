Crossbar-Shaping Roadmap

What's still pre-Crossbar in FrameFlow, ranked by architectural pain it relieves.

Recorded 2026-05-12. Snapshot taken immediately after ADR-0036 (decoded media stream decoupled from playback) landed end-to-end across three commits. The decode layer now speaks fluent Crossbar; the playback layer wraps it as a state machine over pump tasks. This document is the audit of what remains.

Update 2026-05-16 (Crossbar ADR-0010 / ADR-0012). References below to IFrameSink<T> (as a Crossbar substrate type), SupportedMemoryDomains, and "sink inheritance from Crossbar" are stale. The substrate's only sink concept is now the FrameConsumer<TFrame> delegate; FrameFlow's IVideoSink / IAudioSink are standalone IAsyncDisposable interfaces that expose a Consumer property. Substitute mentally: "extends IFrameSink<X>" → "exposes FrameConsumer<X> Consumer"; and ".ToSinkAsync(sink, ct)" → ".ToSinkAsync(sink.Consumer, ct)". The roadmap's tier structure and pain-relief ranking are unchanged.
What "Crossbar-shaped" means. Expose your output as FramePipeline<T>; accept inputs as FramePipeline<T> where applicable; compose via operators (Transform, Observe, Broadcast, ToSinkAsync) rather than register callbacks.

For things that are transforms over frame streams, Crossbar shape is right. For side effects on frames (sinks), Crossbar's IFrameSink<T> is the right shape, and bridges via ToSinkAsync. For stateful coordinators (state machines) Crossbar shape doesn't apply.

Inventory of what's already Crossbar-shaped

  • Decode pipeline — IDecodedMediaStream exposes FramePipeline<IVideoFrame> and FramePipeline<PcmAudioBuffer>. (ADR-0036)
  • Audio resampling — pipeline.Resample(rate, channels) operator in FrameFlow.Audio.
  • AV-sync pacing — pipeline.PacedAgainst(clock, strategy) operator in FrameFlow.Playback. (ADR-0036 Phase 2)
  • Video sink integration — IVideoSink implements Crossbar's IFrameSink<IVideoFrame>; pipeline.ToSinkAsync(videoSink, ct) works directly. (ADR-0030)

Tier 1 — Pixel-domain operators (landed 2026-05-12)

Status: ConvertPixelFormat, Resize, ResizeAndConvert shipped via ADR-0037. Crop and Overlay deferred to follow-ups (see notes below). IFrameConverter marked [Obsolete]; will be removed in a future release.

The new package FrameFlow.Video is the peer of FrameFlow.Audio in both shape and location:

FrameFlow.Audio                     FrameFlow.Video
├─ IAudioResampler        (interface)   ├─ IVideoConverter        (interface)
├─ FfmpegAudioResampler   (swr impl)    ├─ SwScaleVideoConverter  (sws impl)
└─ AudioPipelineExtensions (ops)        └─ VideoPipelineExtensions (ops)

The original audit follows for reference.

IFrameConverter was a placeholder. Defined in FrameFlow.Media but never implemented. PipelineConfig references it; PipelineNegotiator's comment said "Future versions will insert an IFrameConverter when the format or domain requires it." That future arrived as ADR-0037.

OperatorPurposePain it relieves
ConvertPixelFormat(target) swscale-backed YUV↔RGB, planar/packed, bit-depth changes Every video sink today does format conversion internally (Avalonia, SDL). Becomes a composable transform.
Resize(w, h) swscale-backed rescaling Captioning Phase 2 wants a fixed-size preview; YOLO wants 640×640 input; thumbnails; ABR transcoding.
Crop(rect) Extract a sub-rectangle YOLO region-of-interest, multi-camera viewport, picture-in-picture.
Overlay(other, blend) Composite two pipelines Captioning Phase 2 (caption overlay on video) is exactly this. YOLO bounding-box rendering is this. Watermark stamping is this.
ColorSpaceConvert(target) BT.601↔BT.709, sRGB↔linear HDR work eventually; less urgent.

The swscale wrapper for the first three is small (well-understood library, single-input/single-output, naturally fits Transform). Overlay composes two pipelines — Crossbar idioms support this but we don't have an example yet.

Doing this also lets IFrameConverter retire — it's the push-shaped predecessor of these operators, and once they exist no one needs the interface.

Tier 2 — Memory-domain operators (Phase A landed 2026-05-12)

Status: Phase A shipped via ADR-0038. The producer-side seam (a GPU-resident frame type that decoders can yield) plus the ToCpu() readback operator are in place. Phase B (MapToGpu upload direction, GPU-aware sinks, flipping the decoder default to yield GPU when hwaccel is active) is deferred to follow-up commits with separate design work.

What landed:

  • GpuVideoFrame in FrameFlow.Decoding — wraps a cloned AVFrame* via av_frame_clone, exposes the software pixel format (typically Nv12) that readback would produce, throws on IVideoFrame.ToCpu with a redirect to the operator.
  • VideoDecoder.YieldHardwareFrames opt-in flag — default false, so every existing consumer keeps getting CpuVideoFrame like before. Set to true and the decoder yields GpuVideoFrame instead of doing internal av_hwframe_transfer_data + sws_scale.
  • pipeline.ToCpu() operator in FrameFlow.Video — no-op pass-through for CPU frames; for GpuVideoFrame runs av_hwframe_transfer_data + sws_scale internally to produce a tightly-packed Bgra32 CpuVideoFrame.
  • pipeline.AsDomain(target) convenience — selects ToCpu when target = Cpu; throws NotSupportedException for target = Gpu with a pointer to Phase B's MapToGpu.

The original audit follows for reference.

Today, when hwaccel is active (CUDA, DXVA, D3D11VA), the decoder produces GPU-resident frames internally but reads them back to CPU before yielding, because the sinks expect CPU frames. Two layering problems welded together:

  1. Inference consumers can't get GPU frames. YOLO-on-GPU paths get CPU readbacks they'd have to upload back. Whisper-on-GPU (future) same story.
  2. The decoder makes memory-domain decisions for everyone. A consumer that knows their sink wants CPU still gets the readback whether they ask or not.

Phase B (deferred):

  • MapToGpu(domain) — CPU→GPU upload. Requires device-context lifecycle management; needs its own ADR.
  • GPU-aware sinks (D3D11 / Vulkan video presenters) that consume GpuVideoFrame directly without a CPU round-trip.
  • Flipping the decoder default to yield GPU frames when hwaccel is active. Currently breaks every sink consumer without GPU-aware sinks landing first; defer until at least one such sink exists.
  • Per-backend frame sub-interfaces (ICudaVideoFrame, ID3D11VideoFrame) for zero-copy ML / shader access.

Tier 3 — User-domain transforms (Whisper landed 2026-05-12)

Status: Whisper operator shipped via ADR-0039. FrameFlow.Whisper is a new peer package: audio.TranscribeWithWhisper(modelPath, options) turns a FramePipeline<PcmAudioBuffer> into a FramePipeline<Caption>. The live-captioning demo migrated to use it — WhisperAsrWorker, WhisperFormatConverter, and AudioChunk are deleted; the demo's Program.cs is now ~150 lines of orchestration around a single pipeline composition.

Remaining Tier 3 operators (queued for their own ADRs as concrete consumers emerge):

  • YOLO inference. The inference demo's Yolov8InferencePreview doing rent→infer→draw inside an IFrameSink<IVideoFrame> can become frames.DetectWith(yolov8Model) emitting FramePipeline<DetectedFrame> (packets enriched with detection metadata via Crossbar's Enrich). Same pattern as the Whisper operator just landed.
  • Audio metering / leveling. Not implemented yet but a natural fit: audio.MeasureLoudness() → enriched packets with dB metadata.

Tier 4 — Audio sink as Crossbar sink (landed 2026-05-12)

Status: shipped. IAudioSink now implements IFrameSink<PcmAudioBuffer> via default interface methods that bridge PresentAsync → WriteAsync + Dispose. The audio pump in PipelineController dropped the Observe adapter and uses stream.Audio.ToSinkAsync(audioSink, ct) directly — symmetric with the video pump.

Tier 5 — Capture sources + encoder terminals (design captured 2026-05-12)

Status: design ADR shipped (ADR-0040); implementation deferred. The shape for both sides is locked in:

  • ICaptureSource / IVideoCaptureSource / IAudioCaptureSource / IMultimodalCaptureSource in a future FrameFlow.Capture package, each exposing FramePipeline<T> like IDecodedMediaStream from ADR-0036.
  • Per-backend packages (FrameFlow.Capture.MediaFoundation, ...AVFoundation, ...V4L2) mirroring the audio-sink split. Periphery's device topology bridges in via a Camera.FromPeripheryProxy-style factory.
  • IEncoder<TFrame, TPacket> + IMuxer in FrameFlow.Encoding as the dual of decoders + muxers. FrameFlow.Encoding.LibAv provides FFmpeg-backed H264 / AAC / MP4 / MKV first.
  • Composition end-state: camera.Frames.Encode(H264).ToSinkAsync(mux.AddStream(...)) — five concepts, five lines, no bespoke ceremony.

Implementation sized at multiple months when there's a concrete consumer pulling for it (OBS-replication, a recording demo, a webcam example). The ADR lists scopes per subsystem.

Things that should NOT be Crossbar-shaped

For symmetry, the parts of FrameFlow that correctly aren't pipeline-shaped:

  • IPlaybackController — a state machine. Its inputs are commands; outputs are state transitions. Already exposes observable streams (PlaybackStateChanged, PositionTick) which is the right shape for state events. Not a transform.
  • Sink lifecycle methods — IAudioSink.Activate/Pause/Resume/Deactivate describe device state independent of pipeline flow. Have to stay as separate methods.
  • IFrameFlowBootstrapper — native-library init. Not a transform.
  • IMasterClock — a primitive consumed by the PacedAgainst operator. The clock itself is a reading, not a pipeline.
  • State machines (the three Stateless-backed machines inside PlaybackController) — not transforms.

Suggested execution order

  1. Tier 1 first. Pixel operators unlock the captioning demo's next phases, retire IFrameConverter, and the swscale wrapper is a well-trodden path. An ADR for "swscale-backed pixel pipeline operators" carries it cleanly. Estimated scope: 4–6 commits, similar shape to the Resample operator landing.
  2. Tier 4 right after. Making audio sinks implement IFrameSink<PcmAudioBuffer> is a ~50-line change. Drops the audio pump's Observe-wrapped sink call to a direct ToSinkAsync. Tiny but cleans the symmetry.
  3. Tier 3 — Whisper + YOLO operators — once Tier 1 lands. Caption overlay (Tier 1) and Whisper operator (Tier 3) together make the captioning demo essentially stream.Audio.TranscribeWithWhisper().Overlay(stream.Video, …).ToSinkAsync(renderer).
  4. Tier 2 — memory-domain operators — biggest architectural lift, depends on hwaccel maturity. Worth doing before the inference example gets serious about GPU-resident pipelines.
  5. Tier 5 — when the codebase is ready for capture/encode, probably after the captioning + inference demos are fully shipped and OBS-replication starts looking real.

The captioning Phase 2–5 backlog effectively forces Tier 1 first — there's no clean way to do "captions overlaid on video" without an Overlay operator. So that's both the most impactful next step and the one with the most concrete demand behind it.
