# Can Avalonia present a texture Direct3D 12 wrote?

**Date:** 2026-09-28
**Issue:** #429, the presenter half. Spike: `spikes/D3D12PresenterProbe`.

## Question

A player that decodes on D3D12VA, so its inference can read frames on the GPU, shows nothing:
`CompositionInteropVideoView` drops D3D12VA frames. Avalonia's compositor on Windows imports D3D11
textures. Can a texture written by D3D12 reach it, and how is the hand-off synchronised?

## Verdict

**Through a D3D11 device of FrameFlow's, not directly.** Avalonia's default Windows backend accepts
D3D11 textures synchronised by a keyed mutex and nothing else, and a D3D12 resource cannot carry a
keyed mutex. A D3D11 device can open the D3D12 texture and the D3D12 fence, wait on the fence on
the GPU, and copy into a keyed-mutex texture of its own, which the compositor presents. The screen
showed the D3D12 clear colour exactly.

| Avalonia | Backend | Import types | Sync | Direct: D3D12 fence | Bridge: D3D11 keyed mutex |
| --- | --- | --- | --- | --- | --- |
| 11.3.22 | ANGLE (default) | D3D11 global handle, D3D11 NT handle | keyed mutex | context lost | presented |
| 12.1.3 | ANGLE (default) | D3D11 global handle, D3D11 NT handle | keyed mutex | context lost | presented |
| 11.3.22 | Vulkan | Vulkan NT and KMT handles | semaphores | context lost | context lost |

11.3.22 is what `FrameFlow.Avalonia.Windows` resolves.

## Findings

### 1. The D3D12 fence semaphore type is declared but not offered

`KnownPlatformGraphicsExternalSemaphoreHandleTypes.Direct3D12FenceNtHandle` exists in both versions,
but the ANGLE backend reports no semaphore types and only `KeyedMutex` synchronisation for either
D3D11 image type. Importing the fence anyway, the update fails with
`PlatformGraphicsContextLostException`.

### 2. The bridge works, and costs one copy

The D3D12 texture is created in a shared heap and the fence with `D3D12_FENCE_FLAG_SHARED`; both
export NT handles. A D3D11 device on the compositor's adapter opens the texture with
`OpenSharedResource1` and the fence with `OpenSharedFence`, waits on the fence with
`ID3D11DeviceContext4::Wait`, and copies into a BGRA texture created with
`SharedKeyedMutex`. That texture is imported as `D3D11TextureGlobalSharedHandle` and presented with
`UpdateWithKeyedMutexAsync`, the path today's D3D11VA presenter takes. The pixel under the texture
read 255, 64, 0, the clear colour; the pixel beside it read the window's blue.

The copy is the price of the keyed mutex. With the NV12-to-BGRA conversion on D3D12, a D3D12VA frame
takes one conversion and one BGRA copy, where a D3D11VA frame today takes one NV12 copy into the
converter's staging texture and one conversion. Its cost at 1080p is not measured.

### 3. The Vulkan backend takes Vulkan handles only

With `Win32RenderingMode.Vulkan`, the compositor imports only Vulkan opaque handles, so neither a
D3D12 nor a D3D11 texture reaches it. Today's D3D11VA presenter would not work there either.

## Method

The probe creates a 256 by 256 BGRA texture in a shared heap on the compositor's adapter (matched
by the LUID the interop reports), clears it to orange on a D3D12 direct queue, and signals a shared
fence to 1. `direct` imports the texture as `D3D11TextureNtHandle` and the fence as
`Direct3D12FenceNtHandle` and calls `UpdateWithTimelineSemaphoresAsync`, waiting for 1 and asking
for 2. `bridge` does the D3D11 hand-off above. After half a second it reads two screen pixels with
`GetPixel`: one inside the texture, and one outside it, over the window's blue background, which
shows the screen read works.

RTX 3080 Ti, Windows 11, Release build.

## Reproducing

```bash
dotnet run --project spikes/D3D12PresenterProbe -c Release -- bridge
dotnet run --project spikes/D3D12PresenterProbe -c Release -- direct
dotnet run --project spikes/D3D12PresenterProbe -c Release -p:AvaloniaVersion=12.* -- bridge
dotnet run --project spikes/D3D12PresenterProbe -c Release -- direct vulkan
```

Each writes `probe-result-<mode>.txt` beside the project and closes its window.
