# Deferred work

Work that is understood well enough to describe but deliberately not scheduled.
Each entry states the shape of the change and what would unblock it — usually a
real consumer asking for it. Nothing here is a commitment.

_Snapshot taken 2026-06-10. Entries are added by editing this file._

- [ ] Graph substrate: worker-pool sink (parallel sinks behind one input edge) Surfaced while splitting MotionClip's ClipRecorder into a graph topology (recording-gate operator -> ClipEncoderSink, edge EdgeOptions.Buffered). Today a SinkNode<T> is single-consumer (one item at a time). For workloads where the producer outpaces one consumer and you want true throughput (multi-camera capture into N encoders, ML inference across N models, scatter-gather writes) there is no first-class shape for N worker sinks dispatching round-robin / first-available from one input channel. Consumers currently paper over this by spawning Task.Run per item - the exact pattern the ClipRecorder refactor is removing. Concrete shape: WorkerPoolSink<T>(int workers, Func<int, SinkNode<T>> factory) with a load-balancing dispatcher in front of the worker channels. Not needed for MotionClip; add the first time a real consumer wants it. Cleanest home is FrameFlow.Graph.

- [ ] Graph substrate: memory-aware (byte-bounded) backpressure on edges EdgeOptions bounds queue depth by item count. For graphs whose items carry large payloads (clip segments holding many decoded frames, batched inference tensors, raw audio segments) count is a poor proxy for memory pressure: a Buffered(cap=3) edge with 300-frame BGRA-32 segments can hold several hundred MB, and tuning to cap=1 loses the backpressure smoothing. Concrete shape: a metered-edge option where the consumer supplies a Func<T,long> cost function and the edge backpressures on the sum of in-flight costs. Niche today; becomes load-bearing as pipelines move past 480p display resolution. Cleanest home is FrameFlow.Graph. Surfaced by the MotionClip ClipRecorder graph refactor.

- [ ] Latent bug: audio-clock staircase from buffered consumption (AV drift jitter) On the typical playback path (ADR-0003: audio is master clock) the published clock is staircase-shaped at buffer-completion granularity, not ticker granularity. OpenAlAudioSink implements IClockSource and runs a 5 ms PeriodicTimer polling GetPlaybackTimeUnderLock(), which derives the clock from a sample counter (_baseSourceTime + samples/sampleRate). The sample counter only advances when OpenAL finishes consuming an enqueued buffer - discretely, at buffer-completion boundaries (all OS audio sinks - WASAPI, OpenAL, CoreAudio - behave this way). So consecutive 5 ms ticks publish the same sample count for many cycles then jump by one buffer's worth; the clock is quantised to buffer duration (~10-50 ms). Pacing wants sub-frame accuracy and snaps to +/-buffer/2. WallClockSource fallback (audio-less) inherits the 5 ms quantum but never the buffer staircase. Primary fix (software-only, ~50 lines in the ticker): interpolate between consumption events using wallclock - track wallclock at last counter advance, extrapolate published = lastObservedAudioTime + (Stopwatch.Elapsed - wallclockAtLastObservation), snap to ground truth on each real advance (clamp so it never goes backwards). This is what mpv / Chromium / VLC do. Subtleties: drift between wallclock and device rate (re-sync on every advance, do not extrapolate too far); pauses/starvation (detect audio not advancing for > 1 buffer and stop extrapolating, hold last value); seeks (re-anchor immediately, clear extrapolator state). Lower-priority alternatives: sub-buffer device-clock APIs (WASAPI IAudioClock/IAudioClock2; OpenAL AL_SAMPLE_OFFSET unreliable); smaller audio buffers (halves amplitude, trades underrun/CPU). Blocking: ship a drift monitor first (instrumented consumer sampling _clockSubject.Latest at high frequency, log per-tick deltas) so the improvement is measured not assumed. References: src/FrameFlow.Audio.OpenAL/OpenAlAudioSink.cs (RunTickerAsync); src/FrameFlow.Graph/IClockSource.cs; src/FrameFlow.Playback/WallClockSource.cs.
