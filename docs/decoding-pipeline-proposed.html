Proposed: clock as a first-class graph signal

A refinement of the current playback pipeline that hoists the audio→video clock dependency out of an implicit method call and into an explicit observable edge — a hot stream of TimeSpan ticks that any number of consumers can subscribe to.

Proposed evolution of ADR-0035 (IMasterClock) and ADR-0036 (decode/playback decoupling). Generated 2026-05-12. Implemented since: see the banner below.

Superseded by the code, 2026-08-26. Written as a draft discussion artifact — "no ADR yet, no code change". That is no longer true: this proposal shipped. The signal it argues for is FrameFlow.Graph.IClockSource (Latest + WaitUntilAsync(target, ct)), produced by ClockSubject and implemented directly by OpenAlAudioSink and WallClockSource. IMasterClock was retired rather than kept as a facade, which is the option this document mildly preferred. Kept as the record of the argument; read the "current" column as history, not as the tree.

The core idea

Replace the interface IMasterClock.GetPlaybackTime() — which is polled on demand — with a signal IClockSource — a hot observable that publishes TimeSpan ticks. The audio sink stops being a clock provider via inheritance and starts being a clock producer via publication. Video pacing stops polling the clock and starts subscribing to it. The runtime shape (two pumps, audio leads video) is unchanged; the graph topology becomes explicit.

The clock-source primitive

The new Crossbar primitive — call it IClockSource for now — is a single, focused contract:

public interface IClockSource
{
    /// <summary>The latest published value; never blocks.</summary>
    TimeSpan Latest { get; }

    /// <summary>
    /// Completes when the published value reaches or passes <paramref name="target"/>.
    /// Cancellation observed. May complete synchronously if already past.
    /// </summary>
    ValueTask WaitUntilAsync(TimeSpan target, CancellationToken ct = default);

    /// <summary>
    /// Subscribes to all tick values published from now on. The first
    /// emission to a fresh subscriber is the cached <see cref="Latest"/>
    /// (BehaviorSubject semantics).
    /// </summary>
    IAsyncEnumerable<TimeSpan> Subscribe(CancellationToken ct = default);
}

Producers implement a counterpart IClockProducer (or just call a Publish(TimeSpan) method on a concrete ClockSubject) — the implementations are platform-specific (OpenAL sample counter, wallclock Stopwatch, RTSP NPT, test fixture).

The two key operators

WaitUntilAsync is what makes PacedUntil efficient: instead of Task.Delay(predicted_delay), the video pacer awaits the signal directly. If the audio clock pauses (device underrun, manual pause), the video pacer pauses automatically without needing a separate pause gate. If the clock jumps (seek), the pacer wakes immediately.

Subscribe is what makes the diagnostics / UI / subtitle consumers fall out for free: each one is an await foreach (var t in clock.Subscribe()) instead of a polling loop.

What this enables that today's shape doesn't

pause for free, at the right layer

Today: pause cancels the pump CTS, which stops video presentation, but the master clock kept advancing (the audio sink keeps consuming samples until OpenAL is told to alSourcePause). The two clocks drift during pause.

Proposed: pause stops the clock producer from publishing. The video pacer's WaitUntilAsync simply doesn't complete. No separate gate; the pacer is naturally suspended on the signal it depends on.

seek as a clock jump

Today: seek cancels pumps, repositions stream, resets clock, re-spawns pumps. Each consumer of the clock has to react to the discontinuity separately.

Proposed: seek publishes a discontinuity tick. Every subscriber sees the jump at the same moment; WaitUntilAsync for any pre-seek target either fires immediately (we're past it now) or remains suspended (we jumped backwards). One event, fan-out semantics.

drift measurement as a derived signal

An A/V drift monitor that today reads audioClock.GetPlaybackTime() and compares to lastPresentedVideoPts on a timer becomes a stream operator: clock.Subscribe().CombineWith(videoPump.PresentedPts).Select(diff). Same data, no polling cadence to tune.

replay and deterministic tests

A FakeClockSource is a list of (timestamp, value) pairs replayed in order. Tests for A/V sync become "publish this clock sequence; assert which video frames were presented." No Task.Delay in tests, no flake.

What stays the same

  • Two pumps. Audio still pumps from stream.Audio to audioSink.WriteAsync. Video still pumps from stream.Video through PacedUntil to videoSink.PresentAsync. The asymmetry — audio leads, video follows — is fundamental to audio-driven playback and is preserved.
  • Bounded(1) channels. Backpressure semantics are identical. A slow video sink still backpressures the video decoder; a slow audio sink still backpressures the audio decoder.
  • IDecodedMediaStream. The decode side has no opinion on clocks. ADR-0036's seam is unchanged.
  • Pull consumers. stream.Video / stream.Audio still emit unpaced for Whisper, YOLO, capture, transcode. The clock observable is a playback-layer concern; pull consumers ignore it.

What needs to be built

  1. Crossbar primitive: IClockSource + ClockSubject (the writable side), WaitUntilAsync + Subscribe operators. Pure Crossbar — no FFmpeg, no audio.
  2. FrameFlow.Playback operator: PacedUntil(IClockSource) as a pipeline operator. One method, ~10 lines. Replaces PacedAgainst(IMasterClock, ISyncStrategy).
  3. OpenAlAudioSink change: add an internal PeriodicTimer that reads the sample counter every 5ms and publishes to its owned ClockSubject. The GetPlaybackTime() method survives as a thin .Latest facade for any consumer that still wants pull semantics.
  4. WallClockClockSource: a Stopwatch-backed producer for the video-only fallback path. Replaces today's WallClockMasterClock.
  5. DI wiring: register one IClockSource per playback session — the audio sink's owned subject when audio is present, the wallclock producer otherwise. Same decision logic as today, different output type.
  6. Test surface: FakeClockSource with a manual Publish(TimeSpan) method, replacing ControllableClockSyncStrategy.

Open questions

  • Conflation policy. Should Subscribe always deliver every published tick, or conflate to "latest only" when the subscriber is slow? Pacing wants conflation; diagnostics drift measurement wants the full sequence. Likely answer: two flavors, or a parameterized subscribe.
  • Discontinuity signaling. Should seek publish a special "discontinuity" tick (e.g. negative TimeSpan sentinel) so subscribers can react explicitly, or is "value jumped backwards" enough? Probably the latter, with a derived IsDiscontinuous operator if needed.
  • Where the timer lives. Inside OpenAlAudioSink means each sink owns its publication cadence — simple. As a separate ClockPublisher node means timer cadence is a configurable seam. Probably start with the simpler "inside the sink."
  • Does IMasterClock survive at all? Could be retired entirely (everything goes through IClockSource.Latest), or kept as a thin facade for callers who want the pull contract. Mild preference: retire it; one concept is better than two.

One-line summary

The audio→video clock dependency becomes a graph edge: the audio sink publishes sample-counter ticks to a hot observable; the video pacer subscribes and awaits the target PTS; every other clock consumer (UI, diagnostics, subtitles, drift) subscribes the same way. Runtime shape unchanged, topology finally honest.
